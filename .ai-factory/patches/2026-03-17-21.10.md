# Remote speaker not detected during tab capture (Telemost)

**Date:** 2026-03-17 21:10
**Files:** src/content/speakerTracker.ts
**Severity:** high

## Problem

Second speaker (remote participant) not detected during recording on Telemost.
Speaker log shows only self (CutCode I.) for 14.4s and remote (Данил Щ.) for 0.2s,
even though Данил was speaking during the call. All audio transcription segments
attributed to CutCode I.

## Root Cause

Chrome's `chrome.tabCapture` (used in the offscreen document for audio recording)
causes `AnalyserNode.getByteFrequencyData()` to return all zeros for WebRTC
MediaStream sources in the main world. This means the speaker-detector.js script
cannot detect remote speaker audio levels while recording is active.

The flow:
1. Recording starts → offscreen captures tab audio via `getUserMedia({ chromeMediaSource: 'tab' })`
2. First MIC_ACTIVITY arrives → `onSelfSpeaker()` sets `useMainWorld = true`
3. DOM observation is disabled (it's replaced by audio-based detection)
4. But audio-based detection returns 0.0 for all remote WebRTC streams
5. Remote speakers are never detected
6. After recording stops (tab capture ends), audio levels return to normal (25-47)

The critical evidence: diagnostic logs showed `lvl=0.0` for all remote audio elements
during recording, and `lvl=25-47` immediately after recording stopped.

## Solution

Added `onDomRemoteFallback()` method to SpeakerTracker that activates when
`remoteAudioEventsCount === 0` (i.e., audio-based remote detection never worked).
It uses the platform-specific `getActiveSpeaker()` function (DOM observation via
dominant CSS class / aria-label) to detect remote speakers.

Key design decisions:
- Only activates when remote audio events have NEVER been received (clean on/off)
- Filters out self name (self is handled by MIC_ACTIVITY)
- Runs every 300ms in the poll interval alongside onDomSelfCheck
- Uses existing resolveActiveSpeaker() for hysteresis and speaker switching logic

## Prevention

- When adding audio-based detection that replaces DOM observation, always keep
  DOM as a fallback — Chrome's audio pipeline can be disrupted by tab capture
- Test speaker detection WITH recording active, not just standalone
- Monitor `remoteAudioEventsCount` in logs to catch this class of issue early
